# 第 1 章 实时图形学与 OpenGL 概览

## 本章学习目标

读完本章后，你应当能够：

- 说明计算机图形学、离线渲染、实时渲染和计算机视觉分别要解决什么问题。
- 描述从应用程序提交场景数据，到 GPU 生成屏幕图像的大致过程。
- 区分 CPU、GPU、显存、操作系统、图形驱动和图形 API 的职责。
- 理解帧、帧率、帧时间、吞吐量和延迟之间的关系。
- 解释为什么“平均帧率很高”并不一定代表程序流畅。
- 使用简单的测量方法判断一个程序主要受 CPU 限制还是 GPU 限制。

## 1.1 图形学程序在做什么

当我们说“渲染一幅图像”时，通常是指：给定一组关于场景的描述，计算出从某个观察位置看到的二维图像。

场景描述可以包含：

- 几何体：三角形、模型、曲线和地形；
- 材质：颜色、粗糙度、金属度、透明度和纹理；
- 光源：方向、位置、颜色、强度和范围；
- 相机：位置、朝向、视野范围和投影方式；
- 环境：天空、雾、反射探针和全局光照信息；
- 时间和交互状态：动画时间、用户输入、物理状态等。

渲染器将这些信息转换为像素。每个像素最终通常至少包含一个颜色值；在更复杂的渲染系统中，还可能包含深度、法线、运动向量、材质 ID 等辅助数据。

可以把一个最简单的渲染问题抽象为：

```text
场景数据 + 相机 + 光照模型 + 渲染算法 = 一幅图像
```

OpenGL 本身并不负责理解“汽车”“树木”或“角色”这些概念。OpenGL 主要提供一套接口，让应用程序能够把几何数据、纹理、状态和着色器提交给 GPU，并要求 GPU 按指定规则完成绘制。场景管理、模型加载、动画、物理、用户界面和资源组织，通常由应用程序或更高层的渲染引擎负责。

### 1.1.1 计算机图形学的核心问题

计算机图形学研究的是如何使用计算机生成、处理和理解图像以及三维场景。它不仅包括“把三维物体画到屏幕上”，还包括：

- 几何建模：如何表示一个物体的形状；
- 几何处理：如何变换、细分、简化和编辑模型；
- 运动与动画：如何描述物体随时间的变化；
- 光照与材质：如何模拟光线与物体表面的相互作用；
- 可见性：如何判断哪些部分应该被看到；
- 图像合成：如何将多个渲染结果组合为最终画面；
- 图像显示：如何将计算得到的颜色交给显示设备。

在本书中，我们重点关注**实时三维光栅化渲染**。这条路线是 OpenGL 最典型的应用领域，但它只是计算机图形学的一部分。

### 1.1.2 从三维场景到二维图像

以一个带纹理和光照的立方体为例，程序至少需要回答以下问题：

1. 立方体由哪些顶点和三角形组成？
2. 立方体位于世界中的什么位置？
3. 相机位于哪里，正在朝哪个方向看？
4. 哪些三角形位于相机的视野内？
5. 每个三角形覆盖屏幕上的哪些位置？
6. 每个覆盖位置的颜色、深度和法线是多少？
7. 光源如何影响该位置的最终颜色？
8. 被其他物体遮挡的部分是否应该丢弃？
9. 透明物体、阴影、反射和后处理如何参与最终合成？

这些问题不会由某一个函数一次性解决，而是由一系列阶段共同完成。后续章节会分别介绍坐标变换、光栅化、着色器、纹理、深度测试、阴影和后处理。

一个简化的渲染流程如下：

```text
模型与材质
    |
    v
场景更新 --> 相机和光源更新
    |
    v
准备 GPU 资源和渲染状态
    |
    v
提交绘制命令
    |
    v
顶点变换 --> 图元装配 --> 光栅化 --> 片段着色 --> 深度/混合测试
    |
    v
帧缓冲区中的图像 --> 交换到屏幕
```

这里的“片段”不是一定等于最终的“像素”。一个三角形经过光栅化后，会产生可能覆盖屏幕采样位置的片段。片段还要经过深度测试、模板测试和混合等操作，最终才可能写入帧缓冲区中的像素。

### 1.1.3 离线渲染、实时渲染与计算机视觉

这三个领域都处理图像和三维信息，但目标不同。理解它们的边界，可以帮助我们判断算法和工程方案为什么不同。

#### 离线渲染

离线渲染通常不要求在很短时间内完成一帧。它可以使用大量计算资源，花费几秒、几分钟甚至数小时生成一幅高质量图像。

典型应用包括：

- 电影和动画特效；
- 产品宣传图；
- 建筑效果图；
- 高质量视觉预览；
- 科学和工程可视化中的高精度图像。

离线渲染常使用路径追踪、光线追踪、复杂的全局光照和高质量采样。它可以通过增加采样次数来减少噪声，也可以在渲染完成前不断进行更精确的计算。

离线渲染的主要目标通常是：

- 图像质量高；
- 光照结果准确；
- 材质和阴影细节丰富；
- 结果可重复、可保存和可后期处理。

例如，一部动画电影中的某个画面即使渲染了十分钟，只要最终画面符合要求，通常也是可以接受的。因为观众不会要求渲染器在播放时实时计算这幅画面。

#### 实时渲染

实时渲染要求程序不断生成图像，并尽快显示给用户。相机可能每一帧都在移动，光源可能正在变化，角色和物体也可能处于动画过程中。

典型应用包括：

- 电子游戏；
- 交互式三维编辑器；
- 虚拟现实和增强现实；
- 实时数据可视化；
- 仿真训练系统；
- 交互式产品配置器。

实时渲染的核心约束是**每一帧都有时间预算**。如果目标是 60 FPS，那么一帧从开始更新到完成显示，理想预算约为：

```text
1 秒 / 60 帧 = 16.67 毫秒 / 帧
```

这个预算还要由输入处理、游戏逻辑、动画、物理、资源准备、渲染、后处理和操作系统调度共同分担。因此，实时渲染通常会使用各种近似方法：

- 用光栅化快速计算可见表面；
- 用预计算环境光代替完整的全局光照；
- 用阴影贴图近似阴影；
- 用屏幕空间算法近似反射和环境遮蔽；
- 用时间累积、空间滤波或降噪恢复图像质量；
- 根据物体距离使用不同精度的模型和效果。

实时渲染不等于“结果不准确”或“画质一定较低”。它的本质是：在严格的时间预算内，用足够好的近似获得稳定、可交互的结果。

#### 计算机视觉

计算机视觉更关注从图像或视频中提取信息，而不是从场景生成图像。它的输入通常是相机采集的照片、视频帧、深度图或传感器数据，输出可能是：

- 物体检测和分类；
- 人脸、姿态和手势识别；
- 相机位姿估计；
- 深度估计和三维重建；
- 图像分割；
- 运动跟踪；
- 缺陷检测和测量。

可以用下面的方向来区分：

```text
计算机图形学：场景描述  --->  图像
计算机视觉：  图像      --->  场景信息
```

二者也会结合使用。例如，增强现实程序可能先用计算机视觉估计真实相机的位置，再用 OpenGL 将虚拟模型实时渲染到真实画面上。此时，视觉算法负责“理解输入”，图形渲染负责“生成叠加内容”。

#### 三者的工程差异

| 领域 | 主要输入 | 主要输出 | 典型时间约束 | 常见优先级 |
| --- | --- | --- | --- | --- |
| 离线渲染 | 精确场景、材质、灯光 | 高质量图像或序列 | 秒到小时 | 质量、准确性 |
| 实时渲染 | 动态场景、输入、相机 | 连续图像帧 | 毫秒级 | 交互性、稳定帧时间 |
| 计算机视觉 | 图像、视频、传感器 | 分类、位置、深度、结构 | 取决于应用 | 识别准确率、鲁棒性 |

同一个算法在不同领域中的取舍也不同。例如，离线渲染可以为一个像素发射大量光线，而实时渲染往往只能使用少量样本，并通过时空重建改善结果；计算机视觉则可能把 GPU 用于卷积网络或特征匹配，而不是三角形光栅化。

### 1.1.4 为什么实时渲染通常选择 GPU

渲染一个三维场景时，很多工作可以对大量数据重复执行。例如：

- 对每个顶点应用相似的矩阵变换；
- 对每个片段执行相似的材质计算；
- 对每个像素进行颜色合成；
- 对纹理中的大量元素进行相似的采样或计算。

这类工作具有高度的数据并行性。GPU 设计了大量并行执行单元，能够同时处理许多顶点、片段或计算任务。CPU 更擅长复杂的控制流、分支、系统调度和少量任务的低延迟处理；GPU 更擅长对大批量数据应用相似操作。

这不是“CPU 慢、GPU 快”的简单二分。实际性能取决于任务类型：

- 复杂的场景组织和资源管理通常更适合 CPU；
- 大量顶点变换通常适合 GPU；
- 大量像素的相似着色通常适合 GPU；
- 依赖严重、分支复杂且数据量很小的工作，GPU 不一定占优；
- CPU 与 GPU 之间的数据传输和同步本身也有成本。

后续学习 OpenGL 时，要始终记住：OpenGL 调用通常发生在 CPU 代码中，但调用的目的是配置 GPU 状态或向 GPU 提交工作。CPU 发出绘制命令，并不意味着 CPU 亲自计算每一个像素。

### 1.1.5 一个像素是如何形成的

以一个三角形为例，可以把过程简化为以下步骤：

1. CPU 将顶点数据放入 GPU 可访问的缓冲区。
2. 应用程序绑定顶点格式和着色器程序。
3. CPU 发出绘制命令。
4. 顶点着色器处理三角形的每个顶点。
5. GPU 根据变换后的顶点执行图元装配和裁剪。
6. 光栅化器确定三角形覆盖哪些屏幕采样位置。
7. GPU 对覆盖区域执行片段着色器。
8. 深度、模板和混合规则决定片段是否写入目标。
9. 颜色最终写入帧缓冲区。
10. 窗口系统将完成的缓冲区显示出来。

要注意，片段着色器通常不是“每个三角形执行一次”，而是可能对三角形覆盖的许多采样位置执行。一个占据大面积屏幕的三角形，片段着色器的执行次数可能远大于顶点着色器的执行次数。

这解释了两个常见现象：

- 增加模型顶点数量可能影响顶点阶段，但不一定是当前瓶颈；
- 提高窗口分辨率会显著增加片段和后处理成本，即使场景中的模型完全不变。

## 1.2 CPU、GPU、显存、驱动与图形 API 的职责

理解 OpenGL，不能只记住函数名。更重要的是知道一次 API 调用在系统中的位置，以及数据究竟存放在哪里、由谁处理。

### 1.2.1 CPU：应用程序的组织者

CPU 通常负责以下工作：

- 创建窗口和 OpenGL 上下文；
- 读取用户输入和操作系统事件；
- 更新游戏逻辑、动画、物理和场景状态；
- 加载和解析模型、纹理、着色器文件；
- 组织渲染顺序；
- 设置 OpenGL 状态和资源引用；
- 提交绘制、计算和同步命令；
- 处理错误、日志和工具界面。

一个典型的应用层帧循环可以表示为：

```cpp
while (!windowShouldClose()) {
    const float deltaTime = clock.tick();

    pollEvents();
    updateInput();
    updateScene(deltaTime);
    renderer.render(scene);

    swapBuffers();
}
```

这里的 `renderer.render(scene)` 可能只是向 GPU 提交一系列工作，并不保证 GPU 在该函数返回时已经完成所有计算。CPU 和 GPU 通常可以并行工作，这种并行关系是性能分析的基础。

CPU 还负责决定“画什么”和“以什么顺序画”。例如，应用程序可能先绘制阴影深度，再绘制不透明物体，最后绘制透明物体和后处理。GPU 负责按照这些命令执行具体的并行计算。

### 1.2.2 GPU：大规模并行计算设备

GPU 负责执行大量适合并行化的图形和计算工作，典型包括：

- 顶点着色器；
- 图元装配和光栅化；
- 片段着色器；
- 深度和模板测试；
- 纹理采样和过滤；
- 混合与颜色写入；
- Compute Shader；
- 某些硬件级的查询、压缩和显示操作。

GPU 不会主动读取你的 C++ 场景对象。它只能访问已经通过 OpenGL 资源接口上传或映射到 GPU 可访问内存中的数据。一个 C++ 类中的成员变量，只有在你将其整理为合适的缓冲区或纹理后，GPU 才能使用。

GPU 的执行模型和普通 C++ 函数调用不同：

- 一个着色器可能同时为大量顶点或片段执行；
- 相邻执行单元通常以相似的控制流运行；
- 随机访问、分支和同步可能降低效率；
- GPU 工作提交通常是异步的；
- CPU 读取 GPU 结果可能迫使双方等待。

因此，下面两段代码的性能含义完全不同：

```cpp
// CPU 逐个处理大量数据
for (auto& vertex : vertices) {
    vertex.position = transform * vertex.position;
}
```

```cpp
// CPU 提交一次绘制，顶点变换在 GPU 顶点着色器中并行执行
glDrawElements(GL_TRIANGLES, indexCount, GL_UNSIGNED_INT, nullptr);
```

第二段代码并不是“没有计算”，而是把大量相似计算交给了 GPU。

### 1.2.3 显存：GPU 的工作数据空间

显存是 GPU 访问资源的主要存储空间。渲染器可能在显存中存放：

- 顶点缓冲和索引缓冲；
- 纹理和 mipmap；
- 着色器相关数据；
- 深度缓冲和颜色缓冲；
- 阴影贴图；
- G-buffer 和后处理纹理；
- Compute Shader 使用的工作缓冲区。

资源从磁盘到屏幕通常要经历多个层次：

```text
磁盘文件
  -> CPU 内存中的解码数据
  -> 图形驱动管理的资源
  -> GPU 可访问的显存或统一内存
  -> 帧缓冲区
  -> 显示器
```

在独立显卡系统上，CPU 内存和显存通常是不同的物理内存。上传纹理或顶点数据会产生传输成本；将 GPU 结果读回 CPU 也可能产生同步和传输成本。

在集成显卡或统一内存架构中，CPU 和 GPU 可能共享物理内存，但这不代表数据访问没有成本。缓存一致性、内存带宽、访问权限和同步仍然会影响性能。

显存不足时，驱动可能将资源换出到系统内存。由于系统内存和显存之间的访问速度、带宽和延迟存在差异，过度换出会造成严重卡顿。因此，渲染器通常需要进行纹理压缩、mipmap 管理、资源卸载和显存预算。

### 1.2.4 图形驱动：API 与硬件之间的翻译层

图形驱动由硬件厂商提供，负责将图形 API 的命令转换为具体 GPU 能够执行的操作，并管理大量底层细节，例如：

- GPU 命令生成与提交；
- 资源分配和内存放置；
- 着色器编译和优化；
- OpenGL 状态维护；
- 同步和队列管理；
- 与操作系统窗口系统交互；
- 硬件能力与扩展支持；
- 错误检测和调试消息。

应用程序看到的是 OpenGL 定义的接口，不需要知道 NVIDIA、AMD 或 Intel GPU 的具体指令格式。驱动承担了跨硬件实现的适配工作。

但驱动不是没有成本的“黑盒”。以下操作可能触发额外工作：

- 首次使用某个着色器时进行编译；
- 创建或调整大型资源；
- 改变某些管线状态；
- CPU 读取 GPU 结果；
- 让 CPU 等待 GPU 完成；
- 频繁提交大量很小的绘制命令。

这也是为什么一个看似简单的 OpenGL 调用可能耗时不稳定。真正耗时的工作有时会被驱动延迟到后续调用中。

### 1.2.5 图形 API：应用程序和 GPU 的契约

图形 API 是一组由规范定义的函数、对象、状态和执行规则。OpenGL API 规定了应用程序如何：

- 创建和绑定图形资源；
- 配置顶点数据格式；
- 编译和链接着色器；
- 设置纹理、混合、深度和剔除状态；
- 发出绘制或计算命令；
- 查询执行结果和硬件能力。

API 并不等于驱动，也不等于 GPU：

| 层次 | 主要职责 | 例子 |
| --- | --- | --- |
| 应用程序 | 组织场景和渲染逻辑 | C++ 渲染器、游戏、编辑器 |
| 图形 API | 定义可调用的抽象接口和行为 | OpenGL 4.6 Core |
| 图形驱动 | 将 API 命令适配到具体硬件 | 厂商 OpenGL 驱动 |
| GPU | 并行执行图形和计算任务 | 顶点、片段、计算执行单元 |
| 显示系统 | 管理窗口和图像呈现 | 窗口系统、交换链路、显示器 |

OpenGL 是一种**状态机风格**的 API。很多操作会修改当前上下文中的状态，后续调用会使用这些状态。例如，绑定某个 VAO 后，顶点属性配置和绘制命令会作用于当前绑定对象。状态机带来使用便利，但也容易出现状态泄漏和“上一处代码影响下一处绘制”的问题。

本书会逐步建立资源封装和渲染状态管理，避免把所有 OpenGL 调用散落在业务代码中。

### 1.2.6 CPU 与 GPU 的并行关系

一帧并不一定严格按下面的方式串行执行：

```text
CPU 完成第 1 帧 -> GPU 完成第 1 帧 -> CPU 完成第 2 帧 -> GPU 完成第 2 帧
```

更常见的情况是：

```text
时间 --->
CPU: [更新第1帧][提交第1帧][更新第2帧][提交第2帧][更新第3帧]
GPU:          [执行第1帧][执行第2帧][执行第3帧]
```

CPU 可以在 GPU 执行当前帧时准备下一帧。但如果 CPU 提交得太快，GPU 队列可能积压，输入到显示的延迟增加；如果 GPU 太快而 CPU 提交不足，GPU 会空闲，最终帧率受 CPU 限制。

程序中的同步点会改变这种并行关系。比如调用 `glFinish` 要求 CPU 等待 GPU 完成之前提交的工作，适合某些调试场景，却不应作为普通每帧逻辑使用。

## 1.3 帧、帧率、帧时间、吞吐量与延迟

实时渲染的“实时”不是一个模糊的宣传词，而是可以用时间测量的工程约束。最基本的分析单位就是一帧。

### 1.3.1 什么是帧

帧（Frame）是渲染器在某一时刻生成的一张完整图像。一个典型实时应用的一帧可能包括：

1. 读取窗口和输入事件；
2. 计算经过的时间；
3. 更新相机、角色、动画和物理状态；
4. 更新光源、粒子和场景可见性；
5. 准备或上传本帧需要的 GPU 数据；
6. 执行阴影、主场景和后处理 Pass；
7. 绘制用户界面；
8. 将完成的颜色缓冲区提交给窗口系统；
9. 等待或继续准备下一帧。

“完成一帧”既可以指渲染器完成了对离屏帧缓冲区的写入，也可以指图像已经被显示器扫描出来。分析时必须明确采用哪一种定义。

### 1.3.2 帧率 FPS

FPS（Frames Per Second）表示每秒生成多少帧：

```text
FPS = 1 秒 / 平均帧时间
```

如果平均每帧耗时 16.67 毫秒：

```text
FPS = 1000 / 16.67 ≈ 60
```

如果平均每帧耗时 8.33 毫秒，约为 120 FPS；如果平均每帧耗时 33.33 毫秒，约为 30 FPS。

FPS 适合表达总体吞吐能力，但它有一个明显缺陷：平均值可能掩盖卡顿。例如，连续 59 帧各耗时 10 毫秒，随后有一帧耗时 100 毫秒，平均 FPS 仍然可能看起来不错，但用户会明显感觉到一次停顿。

因此，性能分析不能只看平均 FPS，还要观察每一帧的耗时曲线和高分位数。

### 1.3.3 帧时间 Frametime

帧时间是完成一帧所需要的时间，通常以毫秒表示。对于稳定的实时程序，帧时间比 FPS 更直接：

| 目标帧率 | 单帧时间预算 |
| ---: | ---: |
| 30 FPS | 33.33 ms |
| 60 FPS | 16.67 ms |
| 90 FPS | 11.11 ms |
| 120 FPS | 8.33 ms |
| 144 FPS | 6.94 ms |
| 240 FPS | 4.17 ms |

若一帧中 CPU 更新耗时 5 ms，GPU 渲染耗时 12 ms，且两者可以充分重叠，那么整体帧时间可能接近 12 ms，而不是 17 ms。若某个同步点使二者完全串行，则可能接近 17 ms。

一个简化模型是：

```text
帧时间 ≈ max(CPU 帧时间, GPU 帧时间) + 同步与显示开销
```

它不是所有平台上的精确公式，但能帮助我们建立正确直觉。

### 1.3.4 吞吐量和延迟不是一回事

吞吐量表示单位时间内完成多少工作。对于渲染器，常用 FPS 表示帧吞吐量。

延迟表示一个事件发生后，结果经过多长时间才被观察到。交互式图形程序中常见的输入到显示延迟链路是：

```text
用户操作
  -> 操作系统收到输入
  -> 应用程序读取输入
  -> 场景状态更新
  -> CPU 提交渲染命令
  -> GPU 完成图像
  -> 显示系统呈现图像
  -> 显示器刷新到用户眼前
```

高 FPS 通常有助于降低延迟，但并不保证低延迟。例如：

- 程序以 120 FPS 渲染，但提前排队了很多帧；
- VSync、显示器刷新和缓冲策略导致图像等待；
- CPU 读取输入的时机很晚；
- GPU 工作完成后，错过了当前显示刷新周期。

因此，游戏、虚拟现实和交互式编辑器除了关注平均 FPS，还应关注输入采样时机、渲染队列深度、帧排队和显示呈现时间。

### 1.3.5 抖动、卡顿和尾部延迟

如果连续帧时间为：

```text
16 ms, 17 ms, 16 ms, 18 ms, 16 ms
```

用户通常会感觉较稳定。如果帧时间为：

```text
8 ms, 8 ms, 8 ms, 80 ms, 8 ms
```

即使平均值不低，也会出现明显卡顿。

这种波动称为帧时间抖动。常见原因包括：

- 着色器首次编译；
- 纹理或模型临时加载；
- 内存分配和释放；
- 资源从系统内存迁移到显存；
- 阴影贴图或后处理分辨率突然变化；
- GPU 队列等待；
- CPU 线程争用或操作系统调度。

工程上常观察 P95、P99 帧时间：

- P95 表示 95% 的帧不超过该耗时；
- P99 表示 99% 的帧不超过该耗时。

如果目标是 60 FPS，仅报告平均 16 ms 不够。还应检查 P99 是否经常超过 16.67 ms，以及是否存在单独的极端长帧。

### 1.3.6 VSync 与显示刷新

显示器以固定或可变刷新率更新画面。VSync（垂直同步）会让缓冲区交换尽量配合显示器刷新，目的是避免画面撕裂。

当程序没有在一次刷新周期之前完成新帧时，可能要等待下一个周期。以 60 Hz 显示器为例，刷新周期约为 16.67 ms。如果某帧在 16.67 ms 内完成，可以赶上当前刷新；如果晚了一点，可能要等到下一个刷新周期，呈现时间就可能接近 33.33 ms。

VSync 的行为还受到双缓冲、三缓冲、驱动设置和窗口系统的影响。因此，开启 VSync 后看到的 FPS 数值不一定等于渲染器原始计算能力。

VSync 的主要优缺点：

| 方面 | 影响 |
| --- | --- |
| 优点 | 减少撕裂，使显示节奏与刷新周期对齐 |
| 缺点 | 可能引入等待，错过刷新时会出现较明显的时间跳变 |
| 注意 | 它不能替代真正的性能优化，也不能单独解决输入延迟 |

可变刷新率技术可以让显示器在一定范围内适应帧时间变化，但应用程序仍然需要控制长帧和帧时间抖动。

### 1.3.7 CPU 受限和 GPU 受限

假设目标是 60 FPS：

- CPU 准备和提交一帧需要 20 ms，GPU 只需 8 ms：程序主要受 CPU 限制；
- CPU 只需 5 ms，GPU 渲染一帧需要 22 ms：程序主要受 GPU 限制；
- CPU 和 GPU 分别为 12 ms 和 14 ms：两者都接近预算，需要进一步拆分阶段。

可以通过改变负载做初步判断：

| 操作 | 帧率明显改善 | 可能的瓶颈 |
| --- | --- | --- |
| 降低渲染分辨率 | 是 | GPU 片段、后处理或带宽 |
| 降低阴影贴图分辨率 | 是 | 阴影 Pass 或阴影采样 |
| 减少场景物体和绘制调用 | 是 | CPU 提交、驱动开销或顶点处理 |
| 降低片段着色器复杂度 | 是 | GPU 片段着色 |
| 降低模型顶点数 | 是 | 顶点处理或带宽 |

这些实验只能提供线索，不能代替 GPU Timer Query、CPU profiler 和图形调试器。后续章节会建立更准确的测量工具。

### 1.3.8 一个完整的帧预算示例

假设我们要在 60 FPS 下运行一个场景，可以先给出一个粗略预算：

| 阶段 | 预算 |
| --- | ---: |
| 输入和窗口事件 | 0.5 ms |
| 场景、动画和物理更新 | 3.0 ms |
| 可见性和渲染提交 | 2.0 ms |
| GPU 主场景绘制 | 7.0 ms |
| 阴影 Pass | 2.0 ms |
| 后处理与 UI | 1.5 ms |
| 余量 | 0.67 ms |
| 总目标 | 16.67 ms |

这不是必须遵守的固定配方。不同程序的预算会随硬件、分辨率、场景和目标帧率改变。重要的是把“性能”从抽象感觉变成可观察、可分配的时间预算。

### 1.3.9 为什么要测量而不是猜测

看到 FPS 下降时，直觉可能会把问题归因于“模型太复杂”。但真正原因也可能是：

- 一个纹理格式导致带宽浪费；
- 一个透明 Pass 产生了大量过度绘制；
- 着色器中存在昂贵的循环；
- CPU 每帧重复查找 Uniform 位置；
- 资源上传阻塞了渲染线程；
- 某个同步调用让 CPU 等待 GPU。

可靠的性能调查应按以下顺序进行：

1. 记录总帧时间和帧时间曲线。
2. 分别测量 CPU 更新、提交和 GPU 各个 Pass。
3. 改变单一变量，观察性能响应。
4. 使用 RenderDoc 或厂商工具确认热点。
5. 优化后重新运行相同基准场景。

不要用一次运行结果下结论。应固定窗口尺寸、场景、相机路径、资源状态和测试时间，并记录硬件、驱动和构建配置。

## 1.4 小结

本节建立了学习 OpenGL 所需的系统视角：

- 图形学程序将场景描述转换为图像；
- 离线渲染优先考虑质量，实时渲染必须服从毫秒级时间预算，计算机视觉则主要从图像提取场景信息；
- CPU 负责组织和提交工作，GPU 负责大量并行计算，显存保存 GPU 工作资源，驱动负责 API 与硬件之间的适配；
- OpenGL 是应用程序与图形硬件之间的抽象契约，并且具有明显的状态机特征；
- FPS 是吞吐量指标，帧时间更适合分析实时预算，输入到显示延迟则描述交互响应速度；
- 平均 FPS 不能代表全部体验，帧时间抖动、P95/P99 和长帧同样重要；
- 性能优化必须建立在测量和可复现的基准上。

## 1.5 术语表

| 术语 | 含义 |
| --- | --- |
| Frame | 一张完整的渲染图像或一次完整的渲染循环结果 |
| FPS | 每秒生成的帧数，表示吞吐量 |
| Frametime | 生成一帧所需的时间，通常以毫秒表示 |
| Latency | 从输入或状态变化到结果可见所需的时间 |
| Throughput | 单位时间内完成的工作量 |
| Rasterization | 将几何图元转换为覆盖屏幕采样位置的片段的过程 |
| Fragment | 光栅化产生的候选像素数据，仍可能被测试丢弃 |
| Framebuffer | 保存渲染结果的颜色、深度和模板附件的目标 |
| VRAM | GPU 直接访问的显存 |
| Driver | 将图形 API 命令适配到具体 GPU 的软件 |
| VSync | 尝试让缓冲区交换与显示器刷新同步的机制 |
| CPU-bound | 性能主要受 CPU 更新、提交或驱动开销限制 |
| GPU-bound | 性能主要受 GPU 着色、光栅化、带宽或后处理限制 |

### 实践练习：建立第一个帧时间记录器

在当前 C++ 工程中实现一个最小的 CPU 帧时间统计器，要求：

1. 使用 `std::chrono::steady_clock` 测量相邻两帧之间的时间。
2. 计算瞬时 FPS 和最近 120 帧的平均帧时间。
3. 记录最近 120 个帧时间，输出最小值、最大值和近似 P95。
4. 忽略程序启动阶段前 30 帧，避免初始化成本污染统计结果。
5. 在日志中同时输出窗口尺寸、构建配置和 VSync 状态。

示意代码：

```cpp
#include <chrono>
#include <cstddef>
#include <deque>
#include <numeric>

class FrameTimer {
public:
    using Clock = std::chrono::steady_clock;

    void beginFrame() {
        currentFrameStart_ = Clock::now();
    }

    void endFrame() {
        const auto now = Clock::now();
        const double milliseconds =
            std::chrono::duration<double, std::milli>(now - currentFrameStart_).count();

        samples_.push_back(milliseconds);
        if (samples_.size() > maxSamples_) {
            samples_.pop_front();
        }
    }

    double averageMilliseconds() const {
        if (samples_.empty()) {
            return 0.0;
        }

        const double total = std::accumulate(samples_.begin(), samples_.end(), 0.0);
        return total / static_cast<double>(samples_.size());
    }

private:
    Clock::time_point currentFrameStart_{};
    std::deque<double> samples_;
    std::size_t maxSamples_ = 120;
};
```

这段代码只测量 CPU 侧从 `beginFrame()` 到 `endFrame()` 的时间。它不能代表 GPU 已经完成渲染，也不能准确测量输入到显示延迟。后续学习 OpenGL 查询对象和 GPU Timer Query 后，再为它增加 GPU 测量部分。
